# Передача кода: всё, что нужно знать, чтобы править этот сервис

Один документ для того, кто получает копию этого кода и должен привести её к
текущей версии, найти в ней свои ошибки и не завести новых.

**Версия, которую описывает документ:** `main` на коммите `0a799cf`
(«Поправить отставшую прозу про блок задач»), 4 октября 2026.
Сверить: `git log -1 --format=%h origin/main`.

## 0. Как этим пользоваться

Порядок, если у вас на руках чужая или старая копия:

```bash
npm install
npm run диагностика                # какие известные починки отсутствуют
npm test                           # поведение: 72 пробы
npm run проверить-ссылки           # не врёт ли документация про код
```

`диагностика.mjs` проходит по каталогу из [раздела 11](#11-каталог-дефектов) и
ищет в коде **признак** каждой починки — строку, которая есть только когда
починка на месте. Номера в её выводе совпадают с номерами каталога: увидели
`ОТСУТСТВУЕТ №7` — открываете дефект №7 и читаете, чем он опасен, как починен и
какой пробой закрыт.

Это проверка **наличия**, а не работоспособности: признак можно написать, не
починив. Поэтому после диагностики всегда `npm test` — пробы проверяют поведение.

### Главный принцип этого кода

> **Молчаливая потеря данных хуже честного падения.**

Из него выросло почти всё остальное. Пустой ответ, который можно спутать с
«данных нет», обязан становиться ошибкой. Курсор, который не двигает выборку, —
ошибкой. Ноль строк в снимке — ошибкой. Задача, упавшая с внятным текстом в
колонке «Результат», чинится за пять минут. Задача, которая год писала половину
заказов и отмечалась успешной, не чинится вообще: данных за этот год уже нет.

Если вы правите этот код и сомневаетесь — выбирайте падение.

### Чего делать нельзя никогда

| Нельзя | Почему |
|---|---|
| Сдвигать строки на листе «Настройки» | Сервис читает их по номерам из `НАСТРОЙКИ` в `src/schemas.js`, не по заголовкам. |
| Переименовывать листы в книге, не правя `СХЕМЫ` | Имена сверяются посимвольно, включая пробелы. |
| Писать в книгу то, что из книги прочитано | Пометка «текст» (апостроф) обратно не приходит — артикул снова разберётся как дата, формула затрётся своим же значением. |
| Ставить «Обновлено» не последней колонкой | Сравнение строк пропускает именно последнюю. Сдвинете — каждый прогон будет переписывать весь лист. |
| Заворачивать в `текстом()` числовые колонки | Формулы книги перестанут по ним считать. |
| Считать пустой ответ за «данных нет» | Это и есть тихая потеря данных. |
| Гонять задачи параллельно | Лимиты маркетплейсов на аккаунт, а не на метод; получите 429 на всём. |
| Повышать `ПРЕДЕЛ` вместо архивирования | 50 000 строк — уже граница, за которой чтение листа само становится проблемой. |

## 1. Что это за сервис

Воркер на Node (ESM, без сборки, одна зависимость — `googleapis`). Раз в минуту
смотрит в лист «Настройки» Google Таблицы, берёт оттуда список задач и
расписание, ходит в API пяти маркетплейсов и складывает результат в листы той же
книги. Развёрнут на Railway как воркер (публичный порт не нужен).

**Расписанием управляет книга, а не код.** Частота, глубина, период, включение и
выключение — это ячейки на листе «Настройки». Чтобы поменять их, править
исходники не нужно, и это сделано нарочно: менять их должен тот, кто смотрит в
таблицу, а не тот, кто умеет деплоить.

```
Google Таблица «Настройки»              Маркетплейсы
     строки 15–62                 WB · Ozon · Яндекс · Ламода
          │                                  │
          ▼                                  ▼
    config.js ──► index.js ──► коннекторы ──► sheets.js ──► листы книги
   (что и когда)   (цикл)     (как забрать)  (как положить)
```

Имена в коде русские — и файлы проб, и идентификаторы. Это не стилистика: книга,
настройки и сообщения об ошибках на русском, и перевод на латиницу добавлял бы
слой перевода в каждом месте, где код касается данных.

## 2. Карта кода

| Файл | Размер | За что отвечает |
|---|---|---|
| `src/tz.js` | строк десять | Часовой пояс. **Импортируется первым.** |
| `src/index.js` | сотня | Цикл расписания, таблица «задача → коннектор», запись результата. |
| `src/config.js` | сотня с небольшим | Чтение листа «Настройки», разбор строки задачи, отметка запуска. |
| `src/schemas.js` | сотня с небольшим | Единственный источник правды: листы, колонки, ключи, номера строк. |
| `src/http.js` | четверть тысячи | Запросы с повторами, даты, период, защита значений. |
| `src/sheets.js` | под триста | Чтение и запись книги: снимки, дозапись, сравнение, шапка. |
| `src/wb-ozon.js` | под тысячу | Коннекторы Wildberries и Ozon — самый большой модуль. |
| `src/yandex-lamoda.js` | две сотни | Коннекторы Яндекс Маркета и Ламоды. |
| `scripts/свод.mjs` | сотня | Собирает весь код в один документ. |
| `scripts/проверить-ссылки.mjs` | две сотни | Сверяет документацию с кодом по содержимому. |
| `scripts/диагностика.mjs` | две сотни | Ищет в копии кода отсутствующие починки. |

Размеры на глаз: точные числа устареют от первой же правки, настоящие — в выводе
`npm run свод`.

### Почему `tz.js` импортируется первой строкой

В ES-модулях **все** `import` выполняются раньше любого кода файла. Присвоить
`process.env.TZ` прямо в `index.js` — поздно: коннекторы уже импортированы и
успели посчитать даты. В контейнере по умолчанию UTC, и все отметки уезжали на
три часа. Поэтому `tz.js` ничего не экспортирует и стоит первым импортом.

### Как идёт один проход

1. **`тик()`** (`index.js`) срабатывает раз в минуту. Если прошлый проход ещё не
   закончился — тик пропускается (флаг `идёт`).
2. **`задачи()`** (`config.js`) читает блок задач и превращает каждую строку в
   объект задачи. Строки с именами не из списка `ЗАДАЧИ` пропускаются, но
   включённая строка с непохожим именем называется в журнале: опечатка иначе
   неотличима от «срок ещё не подошёл».
3. **`пора()`** отбирает задачи, у которых с прошлого запуска прошло больше
   «Каждые, мин».
4. **`выполнить()`** зовёт коннектор, замеряет время и пишет в книгу «Последний
   запуск» и «Результат». Ошибка коннектора не роняет проход: она ложится в
   «Результат» текстом `ОШИБКА: …`.

Задачи идут **последовательно**. Лимиты у маркетплейсов считаются на аккаунт, и
параллельный проход гарантированно упёрся бы в 429.

### Режимы запуска

| Команда | Что делает |
|---|---|
| `npm start` | воркер: тик раз в минуту, бесконечно. Это запускает Railway. |
| `npm run once` | один проход по тем задачам, которым пора. |
| `node src/index.js --task "Имя задачи"` | одна задача принудительно, мимо расписания. |

## 3. Договор с книгой

### Лист «Настройки»

Номера строк зашиты в `НАСТРОЙКИ` (`src/schemas.js`). **Сдвигать строки нельзя.**

| Что | Диапазон | Константа |
|---|---|---|
| Имя листа | `Настройки` | `лист` |
| Параметры | `A3:B12` | `параметрыОт` / `параметрыДо` |
| Блок задач | `A15:G62` | `задачиОт` / `задачиДо` |
| Дочитывается ниже блока | ещё 5 строк | `задачиЗапас` |

Пять строк ниже блока дочитываются не ради работы, а ради предупреждения: задача,
вписанная за концом блока, иначе не запустилась бы и ничего бы об этом не
сказала. Имена задач — замкнутый список, поэтому ложной тревоги быть не может.
Завели задачу ниже — поднимите `задачиДо`.

### Колонки блока задач

| Кол. | Заголовок | Смысл |
|---|---|---|
| A | Задача | Должна точно совпадать с именем из `ЗАДАЧИ`. |
| B | Вкл | `1` — задача работает. |
| C | Каждые, мин | Интервал. Пусто → 30. |
| D | Глубина дней | Скользящее окно. У возвратов сюда же кладут дату. |
| E | С даты | Граница истории. |
| F | Последний запуск | **Пишет сервис.** Очистить = перезалить историю. |
| G | Результат | **Пишет сервис.** Итог или `ОШИБКА: …`. |

**Почему дата принимается и из D, и из E.** В блоке возвратов обе колонки
озаглавлены «С даты», и неизвестно, в какую человек впишет дату.
`задачаИзСтроки()` берёт ту, что разбирается в **настоящую** дату: настоящая дата
глубиной быть не может, а глубина датой не притворится — год не тот (порог 2015).
Берётся именно разбираемая колонка, а не первая непустая: пробел, ноль или
оставшаяся подпись в E иначе отбросили бы дату из D.

**Метка успеха.** «Последний запуск» отмечает **попытку**: `отметитьЗапуск` пишет
её и при ошибке. Для вычисления периода нужен именно успех — иначе упавший прогон
сдвинул бы окно вперёд, и невыгруженные заказы пропали бы навсегда. Чтобы метка
успеха пережила ошибку, она дописывается в текст «Результата» хвостом
`| успех: ДД.ММ.ГГГГ ЧЧ:ММ:СС` и вычитывается оттуда на следующем прогоне.

### Листы данных

Обычно имя задачи совпадает с именем листа. Единственное исключение: задача
`Возвраты OZON FBS` пишет в лист `Возвраты OZON` — возвраты приходят одним
методом сразу по обеим схемам, и какая схема у конкретного возврата, написано в
колонке «Схема».

| Задача | Лист | Режим | Ключ (индексы колонок) |
|---|---|---|---|
| FBO остатки ВБ | тот же | снимок | — |
| FBS остатки ВБ | тот же | снимок | — |
| Заказы ВБ FBO | тот же | дозапись | `[0]` srid |
| Заказы ВБ FBS | тот же | дозапись | `[0]` задание |
| FBS Возвраты | тот же | дозапись | `[0,2]` возврат + баркод |
| **WB заказы проверка** | тот же | дозапись | `[0]` srid |
| FBO остатки ОЗОН | тот же | снимок | — |
| FBS остатки ОЗОН | тот же | снимок | — |
| Заказы ОЗОН FBO | тот же | дозапись | `[0,4]` отправление + артикул |
| Заказы ОЗОН FBS | тот же | дозапись | `[0,4]` |
| **Возвраты OZON FBS** | **Возвраты OZON** | дозапись | `[0]` возврат |
| FBO/FBS остатки Яндекс | тот же | снимок | — |
| Заказы Яндекс FBO/FBS | тот же | дозапись | `[0,2]` заказ + артикул |
| FBO/FBS остатки Ламода | тот же | снимок | — |
| Заказы Ламода FBO/FBS | тот же | дозапись | `[0,2]` |
| FBO/FBS остатки Мвидео | тот же | снимок | вручную |
| Заказы Мвидео FBO/FBS | тот же | дозапись | вручную |

Снимок — любой лист, в имени которого есть слово «остатки» (`СНИМКИ`). Это
удобно, но помните об этом, называя новый лист.

Полные схемы колонок — в `src/schemas.js`, раздел `СХЕМЫ`. Дублировать их здесь
значило бы завести второе место, где они расходятся с кодом.

Два правила, общие для всех листов:

* **«Обновлено» всегда последняя.** Сравнение строк её игнорирует — иначе каждый
  прогон считал бы изменившимися все строки.
* **Правее колонок схемы лежат служебные колонки книги** — ключи окна, недели,
  месяца. Их считают формулы, сервис до них не дотягивается: ширина записи
  ограничена длиной схемы.

## 4. Реестр: хосты, методы, ключи, пределы

### Хосты

| Константа | Адрес | Переопределяется |
|---|---|---|
| `WB_СТАТ` | `https://statistics-api.wildberries.ru` | нет |
| `WB_АНАЛИТИКА` | `https://seller-analytics-api.wildberries.ru` | `WB_ANALYTICS_URL` |
| `WB_МАРКЕТ` | `https://marketplace-api.wildberries.ru` | нет |
| `WB_КОНТЕНТ` | `https://content-api.wildberries.ru` | `WB_CONTENT_URL` |
| `OZ` | `https://api-seller.ozon.ru` | `OZON_API_URL` |
| `ЯМ` | `https://api.partner.market.yandex.ru` | нет |
| `LM` | `https://public-api-seller.lamoda.ru/api` | `LAMODA_API_URL` |
| `МВ` | `https://omni-net.sellers.mvideo.ru` | `MVIDEO_API_URL` |

Три адреса вынесены в окружение **только ради проб**: повадки методов — пределы
периода, пагинацию, лимиты — на живом API не проверить. В бою их не задают.
Функция `подставной(у)` узнаёт подставной адрес по `127.0.0.1` или `localhost` и
на нём обнуляет паузы. Проверка именно на localhost, а не «задана ли
переменная»: выставь кто-нибудь `OZON_API_URL` на боевой хост — и паузы исчезли
бы разом у отправлений и возвратов.

### Методы

**Wildberries** (заголовок `Authorization: <токен>`, без `Bearer`):

| Метод | Хост | Задача |
|---|---|---|
| `GET /api/v1/supplier/orders?dateFrom=…&flag=0` | статистика | Заказы ВБ FBO |
| `GET /api/v1/supplier/sales?dateFrom=…&flag=0` | статистика | признак выкупа |
| `POST /api/analytics/v1/stocks-report/wb-warehouses` | аналитика | FBO остатки ВБ |
| `GET /api/v1/analytics/goods-return?dateFrom=…&dateTo=…` | аналитика | FBS Возвраты |
| `POST /api/analytics/v1/order-feed` | аналитика | WB заказы проверка |
| `GET /api/v3/warehouses` | маркетплейс | склады FBS |
| `POST /api/v3/stocks/{складID}` | маркетплейс | FBS остатки ВБ |
| `GET /api/v3/orders?limit=1000&next=…&dateFrom=…` | маркетплейс | Заказы ВБ FBS |
| `POST /api/v3/orders/status` | маркетплейс | статусы заданий |
| `POST /content/v2/get/cards/list` | контент | справочник карточек |

`flag=0` — фильтр по `lastChangeDate`, а не по дате заказа: подхватываются и
изменения в уже выгруженных заказах.

**Ozon** (заголовки `Client-Id` и `Api-Key`):
`POST /v2/analytics/stock_on_warehouses`, `POST /v4/product/info/stocks`,
`POST /v3/posting/fbo/list`, `POST /v4/posting/fbs/list`, `POST /v1/returns/list`.

**Яндекс Маркет** (заголовок `Api-Key`):
`POST /campaigns/{кампания}/offers/stocks`, `GET /campaigns/{кампания}/orders`.
FBY и FBS — **разные кампании**; подставишь чужой номер, метод вернёт пустой
список без ошибки, и это легко не заметить.

**Ламода** (Seller Partner API v2, `Authorization: Bearer` + `sellerId`):
`POST /v2/auth-token`, `GET /v2/fbo/stocks`, `GET /v2/fbs/stocks`,
`GET /v2/orders` и `GET /v2/orders/{orderId}`, `GET /v2/nomenclatures`.

**М.Видео** (omninet, ключ в `api-key`, на 401/404/`OPERATION_NOT_SUPPORTED` — повтор с `Authorization: Bearer`, №49):
`POST /v1/product/stock/info`, `POST /v1/order/fbs/list`, `POST /v1/order/dbs/list`,
`POST /v1/product/mapping/list`; для FBO — `POST /v1/order/fbo/list` и
`POST /v1/market/location/list`, а остатки FBO — тем же `stock/info`: строками
со складом площадки, а если без фильтра их нет — запросом в форме FBO, с
`filter.market_location_ids` (№51). FBO описан в стандарте omninet
(omni-net.dev/spec/api/fbo); подключён ли он кабинету, говорит сам шлюз —
см. №47 и №48. **Проверено в проде 05.11.2026 с обеими схемами ключа: заказов
FBO шлюз М.Видео не отдаёт** — `/v1/order/fbo/list` отвечает 404 и с `api-key`,
и с Bearer, телом маршрутизатора («Not Found» с путём): маршрута нет. Остатки
без фильтра — 40 нулевых строк своего склада, в форме FBS.

### Переменные окружения

| Переменная | Обязательна | Для чего |
|---|---|---|
| `SHEET_ID` | да | идентификатор книги из её адреса |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | да | ключ сервисного аккаунта: сырой JSON или base64 |
| `WB_STATS_KEY` | для ВБ FBO | статистика: заказы и продажи |
| `WB_ANALYTICS_KEY` | для остатков FBO, возвратов и ленты | категория «Аналитика». Пусто → берётся `WB_STATS_KEY`, но у него обычно нет нужной категории |
| `WB_MARKET_KEY` | для ВБ FBS **и для ленты заказов** | остатки, задания, карточки |
| `OZON_CLIENT_ID`, `OZON_API_KEY` | для Ozon | один доступ на обе схемы |
| `YM_API_KEY` | для Яндекса | |
| `YM_CAMPAIGN_FBY`, `YM_CAMPAIGN_FBS` | для Яндекса | **разные** номера кампаний |
| `LAMODA_CLIENT_ID`, `LAMODA_CLIENT_SECRET` | задачи Ламоды | Seller Partner API v2, токен по OAuth |
| `LAMODA_SELLER_ID` | задачи Ламоды | Seller Shop ID, если токен его не несёт |
| `MVIDEO_API_KEY` | задачи М.Видео | ключ API поставщика omninet |
| `TZ` | нет | по умолчанию `Europe/Moscow` |
| `OZON_API_URL`, `WB_ANALYTICS_URL`, `WB_CONTENT_URL` | нет | **только для проб** |

Ключи проверяются лениво: `требовать(...)` роняет **ту задачу**, которой ключа не
хватило, а не весь сервис. Остальные задачи продолжают работать. Сервисному
аккаунту нужен доступ к книге на редактирование; его почта — в поле
`client_email` внутри ключа.

## 5. Период выгрузки

Это место, которое чаще всего понимают неправильно. Реализация — `период()` в
`src/http.js`.

**«С даты»** — граница истории. Раньше неё не ходим никогда. С неё же идёт
первичная заливка, пока «Последний запуск» пуст.

**«Глубина дней»** — скользящее окно, которое обновляется каждый прогон: свежие
заказы добавляются, изменения в уже записанных подхватываются.

```
режим «заливка»   есть «С даты», успешных прогонов не было
                  → берём всё от «С даты» до сегодня

режим «окно»      обычный прогон
                  начало = сегодня − глубина
                  если сервис простоял дольше глубины,
                     окно растягивается назад до прошлого успеха (минус час запаса)
                  и в любом случае не раньше «С даты»
```

Запас в час — на заказы, появившиеся во время самого прогона, и на расхождение
часов.

**Как перезалить историю:** очистить «Последний запуск». Одной правки «С даты»
мало — окно про неё не знает. Сервис сам пишет об этом в «Результат»:
`…; чтобы догрузить историю с «С даты», очистите «Последний запуск»`.

**У возвратов период считается иначе.** И у Ozon, и у ВБ берётся
`границаИстории()` — «С даты» сама по себе, без глубины и водяного знака. У Ozon
потому, что метод принимает только одну дату-фильтр за запрос; у ВБ — потому что
отчёт и так режется на окна по 30 суток.

`период()` возвращает ещё и `растянутоЗнаком` — признак того, что начало окна
взято из водяного знака, а не из глубины. Коннектор, который сужает окно под
предел своего метода, по этому признаку отличает дыру в истории от штатного
излишка. Это важно: один текст на оба случая — это ложь.

## 6. Запись в книгу

### Два режима

**Снимок** (все листы «остатки»): лист перезаписывается целиком. Остаток — это
состояние на момент запроса, история в нём не нужна.

Порядок шагов важен: **сначала пишем, потом убираем хвост.** Обрыв между шагами
оставит лист с данными, а не пустым. И отдельная проверка: пустой ответ не
перезаписывает снимок, а роняет задачу — иначе временный сбой у маркетплейса
стёр бы лист и отметился в книге как успешный прогон.

**Дозапись** (заказы и возвраты): строка с тем же ключом обновляется, новая
уходит в конец. Строки за пределами периода не трогаются — поэтому сузить
«Глубина дней» безопасно, накопленная история никуда не денется.

### Ключи строк

`КЛЮЧИ` в `schemas.js` — индексы колонок, по которым ищется строка при дозаписи.
Ключ считается **тем же приведением**, что и сравнение строк (`сравнимо`). Книга
возвращает значения по-своему — штрихкод числом, `0468…` без ведущего нуля, — и
сырое сравнение не нашло бы такую строку в указателе, дописывая её заново при
каждом прогоне, пока лист не упрётся в предел.

Длинное целое в `сравнимо` остаётся **текстом**: `Number()` держит пятнадцать
значащих цифр, а `srid` бывает девятнадцатизначным. Без этого пять разных заказов
свелись бы к одному ключу.

### Не изменившиеся строки не переписываются

Иначе каждый прогон гонял бы в Таблицы весь лист целиком ради одной только
колонки «Обновлено»: на листе с 17 тысячами заказов это две сотни тысяч ячеек за
прогон.

### Шапка

Заголовки дозаполняются **ровно в пустые клетки** первой строки и отдельными
диапазонами. Занятая клетка не трогается вовсе: там может стоять своя
формулировка или формула, и переписать её значением значило бы её потерять.

## 7. Защита значений от Google Таблиц

Книга пишется с `USER_ENTERED`, то есть Таблицы разбирают всё, что им прислали.
Без защиты:

* артикул продавца `1970-01-29` → дата;
* штрихкод `0012345` → число `12345`;
* название, начинающееся с `=`, → формула;
* размер `12-31` → 12 декабря текущего года;
* `srid` из девятнадцати цифр → потеря последних цифр.

Три функции, и их нельзя путать:

| Функция | Когда | Что делает |
|---|---|---|
| `текстом()` | артикул, штрихкод, размер, название | ставит апостроф **только** если значение действительно переиначат |
| `строгоТекстом()` | длинные идентификаторы, особенно ключи строк | ставит апостроф всегда |
| ничего | SKU, цена, количество, nmID | числа, по которым книга считает формулами |

Трогается только то, что переиначат: обычные числа проходят как есть, иначе
формулы книги перестали бы по ним считать. Таблицы апостроф снимают сами — в
ячейке остаётся ровно то, что прислал маркетплейс.

**Обратное преобразование — `изТаблицы()`.** Книга читается с
`UNFORMATTED_VALUE`, поэтому дата приходит **числом**, днями от 30.12.1899.
Отдавать такое число конструктору `Date` нельзя: он считает его миллисекундами и
получает 1970 год, а строку `46249` — номером года. Оба случая раньше молча
уезжали в запросы к маркетплейсам и давали и 400, и 429, и вечно истинное
`пора()`.

Запасной разбор строк — **только для ISO**: `new Date('01.08.2026')` читает дату
по-американски, а мусор молча превращает в дату. Дата без времени читается
**местной** полуночью, как и запись `ДД.ММ.ГГГГ`: `new Date('2026-09-01')` даёт
полночь по Гринвичу, то есть три часа ночи по Москве.

**Наружу даты уходят двумя способами.** `локальныйISO()` — без смещения, так его
ждут статистика ВБ и Яндекс. `сСмещением()` — с явным смещением от UTC
(`2026-10-01T12:00:00+03:00`), так его ждёт лента заказов ВБ. Разница не
косметическая: без смещения остаётся гадать, прочтёт метод время московским или
всемирным, а ошибка на три часа в границе периода выглядит как успешная выгрузка.

## 8. Коннекторы: что важно про каждую площадку

### Wildberries

Четыре хоста и до трёх токенов разных категорий.

* **Статистика:** заказы и продажи FBO. Лимит — один запрос в минуту **на
  аккаунт**, не на метод. Паузу сервис держит сам (`неЧаще`), поэтому «Заказы ВБ
  FBO» не могут отработать быстрее минуты: это два запроса с обязательной паузой.
  Счётчик паузы живёт в модуле и переживает проход.
* **Аналитика:** остатки FBO, возвраты, лента заказов. Нужен токен категории
  «Аналитика». Остатки FBO приходят построчно, строка на размер; разбивки по
  складам нет — WB отдаёт единственный псевдосклад. Ни штрихкода, ни артикула
  продавца в ответе нет, они берутся из справочника карточек.
* **Маркетплейс:** остатки и задания FBS. Метод остатков принимает только явный
  список баркодов, поэтому сначала обходятся карточки.
* **Контент:** справочник карточек. Нужен остаткам FBS, остаткам FBO, возвратам и
  ленте заказов, поэтому результат кэшируется на 5 минут — ровно на время
  прохода. Дольше незачем: карточки меняются.

**Возвраты ВБ** режутся на окна по 30 суток (предел метода — 31) с лимитом один
запрос в минуту. Год истории — это дюжина окон и дюжина минут, и всё это время
проход занят. Дальше 24 окон задача падает намеренно.

**Лента заказов** (`order-feed`, задача «WB заказы проверка») — отдельный метод
на отдельном хосте, со своим токеном, своим счётчиком лимита и своим
расписанием; с «Заказы ВБ FBO» и «Заказы ВБ FBS» не связан.

Три особенности, которые видны в листе:

1. **Период считается по времени текущего статуса** (`updatedAt`), а не по дате
   оформления. Заказ, оформленный месяц назад и отменённый вчера, попадёт в
   сегодняшнее окно — это и нужно для сверки. Из этого же следует, что по колонке
   «Дата заказа» период не сходится: она бывает раньше начала окна, и это не
   ошибка.
2. **Глубже 31 суток метод не отдаёт ничего** — на более раннюю дату отвечает
   400. Период обрезается до 30 суток. «С даты» старше месяца этому листу истории
   не добавит, сколько её ни правь.
3. **Пагинация идёт `offset`-ом, но по снимку.** Со второго запроса передаётся
   `snapshotTime` из ПЕРВОГО ответа, в первом его быть не должно. Снимок в каждом
   ответе ещё и сверяется. Конец выборки подтверждает **пустая** страница, а не
   короткая: ни `has_next`, ни общего числа метод не отдаёт.

Лимит ленты — один запрос в минуту на аккаунт, у токена категории **«Базовый» —
один запрос в три часа**, и выборка длиннее одной страницы на нём невозможна.

### Ozon

Один ключ на обе схемы. Главная особенность — **пагинация**. Подробный разбор
случая — в [`ozon-pagination.md`](ozon-pagination.md).

Списки отправлений отдают не больше сотни за раз. Листать их `offset`-ом
**нельзя**: у методов нового поколения такого поля нет, а неизвестные поля метод
молча выбрасывает — поэтому запрос выглядел рабочим, отвечал 200 и на любой
странице отдавал одну и ту же первую сотню.

Обход идёт **лестницей**, каждая ступень включается сама, когда предыдущая
перестаёт двигать выборку:

1. курсор метода;
2. рез окна по дате последнего прочитанного отправления;
3. делёж окна пополам.

Нижние две ступени опираются только на фильтр по датам, который заведомо
работает — им всё равно, чем именно метод листается и листается ли вообще.

Двигать **начало** окна по дате страницы нельзя: это молчаливая ставка на то, что
метод сортирует ровно по тому полю, по которому считает период. Разойдись они —
начало перескочит через хвост сортировки, и отправления пропадут без единого
слова. Рез конца такой ставки не делает.

Правая половина после реза начинается миллисекундой **раньше** точки реза:
понимание границ у метода неизвестно, и пойми он строго обе — отправление ровно
на шве выпало бы из обеих половин. Перекрытие снимет указатель прочитанных.

**Возвраты Ozon** листаются `last_id` и приходят одним методом сразу по обеим
схемам. Фильтр по дате метод может молча не применить, поэтому сервис считает,
сколько записей пришло вне запрошенного отрезка, и пишет `ФИЛЬТР НЕ ПРИМЕНЁН`.

### Яндекс Маркет

FBY и FBS — **разные кампании**. Метод заказов не принимает интервал длиннее 30
суток: на 33 днях отвечает 400. Период режется на окна по 28 дней. Заодно:
заказы, доставленные или отменённые больше 30 дней назад, этот метод не отдаёт
вовсе — **глубже месяца история отсюда не берётся**. Даты приходят в
`ДД-ММ-ГГГГ`, конструктор `Date` такое читает неверно.

### Ламода

Seller Partner API v2 на `public-api-seller.lamoda.ru/api`. Доступ — OAuth:
`LAMODA_CLIENT_ID` и `LAMODA_CLIENT_SECRET` меняются на токен, токен обновляется
за минуту до конца и сразу по 401. Каждый метод требует ещё и `sellerId` —
`LAMODA_SELLER_ID`, иначе из самого токена, иначе первый партнёр из
`v1.partner.list`.

Список заказов отдаёт только шапки, позиции берутся из карточки каждого заказа
отдельным запросом — и карточки свежего заказа может ещё не быть (№45).
Признака схемы в заказе нет: FBO или FBS определяется по остаткам. Суммы — в
копейках.

### М.Видео

API по стандарту omninet (omni-net.dev/spec), шлюз `omni-net.sellers.mvideo.ru`,
запасной — `api.omniom.ru` (№46). Со своего склада две схемы, FBS и DBS, — оба
потока идут в «Заказы Мвидео FBS», схема в колонке «Схема». Со склада площадки —
FBO: заказы из `/v1/order/fbo/list`, а остатки приходят тем же `stock/info`,
что и у FBS, и различаются складом строки (№47); без FBO-строк остатки
спрашиваются и в форме FBO, по складам площадки (№51). Подключён ли FBO
кабинету, говорит сам шлюз (№48). На 05.11.2026 шлюз М.Видео заказов FBO не
отдаёт: 404 с обеими схемами ключа, маршрута нет. В остатках без фильтра — только
свой склад. Листы FBO по-прежнему заливаются из кабинета.

Ключ. Стандарт omninet (omni-net.dev/spec/fbo/common/auth) велит для всех схем
один способ — `Authorization: Bearer`; собственный OpenAPI стандарта для FBS/FBO
пока описывает пару `Client-Id` + `Api-Key`, и стандарт называет это
расхождением. Шлюз М.Видео по своей документации и на деле принимает `api-key`,
поэтому он первый, а на 401, 404 и `400 OPERATION_NOT_SUPPORTED` тот же запрос
повторяется с одним Bearer (№49).
Прошла одна из схем — её данные, схема запоминается для метода (общей схемы
нет), и в «Результате» стоит «ключ в Authorization: Bearer», если это Bearer.
Не прошла ни одна — решает ответ `api-key`, а ответ Bearer — только если
`api-key` отвергнут (401); другой ответ дописан справкой. Если Bearer не прошёл,
а `api-key` не получил 401, всё — как до этой правки, кроме двух ответов
метода: 404 заказов FBO не меняет адрес шлюза (№50), а неподключённый DBS
терпится и по решающему `400 OPERATION_NOT_SUPPORTED`, как по 404/403.

Первая страница списка пробуется в трёх видах тела: шлюз на неподходящее тело
отвечает голым «HTTP 400». Цены — целые, умноженные на 100.

## 9. Как обновить чужую копию

Если у вас копия, разошедшаяся с этой версией, порядок такой.

**Шаг 1. Понять, насколько разошлась.**

```bash
npm run диагностика -- --всё
```

Вывод делит починки на «на месте» и «ОТСУТСТВУЕТ». Отсутствующие — это и есть
список ваших дефектов, с номерами каталога.

**Шаг 2. Чинить по возрастанию номера.** Нумерация не случайна: она идёт от
основания к частностям. Дефекты 1–6 — про разбор дат и защиту значений, и от них
зависит всё остальное; починив пагинацию, но не починив `изТаблицы`, вы получите
исправный обход неправильного периода.

**Шаг 3. На каждую починку — проба, про которую доказано, что на прежнем коде она
падает.** Как это проверить — [раздел 12](#12-метод-как-здесь-принято-работать).

**Шаг 4. Сверить документацию.**

```bash
node scripts/проверить-ссылки.mjs
```

**Шаг 5. Если ваша копия разошлась по структуре** (другие имена листов, другие
номера строк настроек) — правьте `src/schemas.js`, а не коннекторы. Это
единственный источник правды по структуре книги, и всё остальное читает её
оттуда.

### Чего в копии может не быть вовсе

Эти части появились поздно, и в старой копии их может не быть целиком:

| Что | Файл | Зачем |

| Возвраты ВБ | `src/wb-ozon.js`, `wbВозвраты` | лист «FBS Возвраты» |
| Возвраты Ozon | `src/wb-ozon.js`, `ozonВозвраты` | лист «Возвраты OZON» |
| `строгоТекстом`, `сСмещением` | `src/http.js` | защита длинных id и дат со смещением |
| `подставитьКлиент` | `src/sheets.js` | шов для проб: без него запись в книгу не проверить |
| `задачиЗапас` | `src/schemas.js` | предупреждение о задаче ниже блока |
| Пробы | `проба/` | шесть файлов, 72 случая |

## 11. Каталог дефектов

Пятьдесят одна починка. Каждая — из настоящей поломки, не из предосторожности.
Номера совпадают с выводом `npm run диагностика`; он считает ещё и одну проверку
на лишнее (не вернулся ли `offset` в тело запроса отправлений Ozon), поэтому
печатает 52.

Формат: **признак** — как дефект проявляется; **причина** — почему; **починка** —
что сделано; **чем закрыто** — какая проба падает без починки.

### А. Даты и время (№1–№3, №44)

**№1. Серийная дата из книги разбиралась как миллисекунды.**
*Признак:* Ozon и Яндекс отвечают 400, ВБ — 429, `пора()` всегда истинно, период
уезжает в 1970 год. Выгрузка при этом может выглядеть успешной.
*Причина:* книга читается с `UNFORMATTED_VALUE`, и дата приходит **числом** —
днями от 30.12.1899. `new Date(46249)` — это 1970 год плюс 46 секунд, а
`new Date('46249')` — 46249-й год.
*Починка:* `изТаблицы()` в `src/http.js` собирает дату по календарным частям от
эпохи Таблиц. Отбрасывает значения ≤ 0 и > 100 000 — осмысленное лежит между 1900
и 2100 годом.
*Чем закрыто:* `проба/настройки.test.js` — разбор строки задачи на серийных датах.

**№2. Запасной разбор строки хватал что угодно.**
*Признак:* мусор в ячейке «С даты» молча становится датой, период уезжает на
месяцы, прогон успешен.
*Причина:* `new Date(текст)` для `01.08.2026` читает дату по-американски, а для
мусора возвращает то, что сумеет.
*Починка:* запасной разбор только для ISO; всё остальное — `null`, и тогда
`границаИстории` скажет понятное «не разобрана «С даты»».

**№3. ISO-дата без времени читалась полночью по Гринвичу.**
*Признак:* первичная заливка начинается на три часа позже указанного дня. Заливка
бывает один раз, поэтому эти три часа теряются навсегда.
*Причина:* `new Date('2026-09-01')` — полночь UTC, то есть 03:00 по Москве, тогда
как `ДД.ММ.ГГГГ` разбирается местной полуночью. Две записи одной даты расходились.
*Починка:* дата без времени собирается по частям как местная; запись со
смещением по-прежнему отдаётся конструктору как есть.
*Чем закрыто:* `проба/настройки.test.js` — «ISO-дата текстом читается местной
полночью».

**№44. Часовой пояс задавался слишком поздно.**
*Признак:* все отметки времени на три часа раньше.
*Причина:* в ES-модулях все `import` выполняются раньше кода файла, поэтому
`process.env.TZ = …` в `index.js` ничего уже не меняет: коннекторы импортированы.
*Починка:* отдельный `src/tz.js` первым импортом, ничего не экспортирует.

### Б. Значения и Google Таблицы (№4–№9, №12)

**№4. Таблицы переиначивали артикулы и штрихкоды.**
*Признак:* артикул `1970-01-29` в листе стал датой, штрихкод `0012345` — числом
`12345`, название с `=` — формулой, размер `12-31` — 12 декабря.
*Причина:* книга пишется с `USER_ENTERED` — Таблицы разбирают всё.
*Починка:* `текстом()` ставит апостроф там, где значение действительно
переиначат. Регулярка `ПЕРЕТОЛКУЕТ` ловит `=+-@` в начале, ведущий ноль,
двух- и трёхчастные даты, время. Точку в двухчастном случае нарочно не ловит:
`3.7` и `100.50` — обычные числа.

**№5. Длинный идентификатор терял хвост.**
*Признак:* `srid` из девятнадцати цифр в листе оканчивается нулями.
*Причина:* Таблицы держат пятнадцать значащих цифр. `текстом()` длинное число не
трогает — ни один его шаблон на него не похож.
*Починка:* `строгоТекстом()` ставит апостроф всегда. Применяется к `srid` ленты
заказов — колонке, которая служит ключом строки.

**№6. Дата уходила без смещения туда, где смещение обязательно.**
*Признак:* граница периода ленты заказов уезжает на три часа.
*Причина:* `локальныйISO()` даёт время без смещения; метод ленты ждёт его со
смещением (так и в примере метода), и остаётся гадать, прочтёт он время
московским или всемирным.
*Починка:* `сСмещением()` добавляет явное смещение от UTC.
*Чем закрыто:* `проба/лента-заказов-вб.test.js` — «даты уходят с явным смещением».

**№7. Ключ строки схлопывал длинные идентификаторы.**
*Признак:* пять заказов записались как один; на следующем прогоне новый заказ
затёр чужую строку. История теряется построчно, прогон успешен.
*Причина:* `ключОт()` считает ключ через `сравнимо()`, а то приводило числовые
строки к числу. `Number()` держит пятнадцать значащих цифр — девятнадцатизначные
`srid`, различающиеся в последних цифрах, давали один ключ.
*Починка:* в `сравнимо()` целое длиннее пятнадцати цифр остаётся текстом.
Числовое приведение там ничего и не чинило: в обе стороны такое число не ходит.
*Чем закрыто:* `проба/лист.test.js` — «девятнадцатизначные srid не схлопываются».

**№8. Сравнение строк сводило к числу помеченный текст.**
*Признак:* испорченный ранее артикул `0012345` не чинится никогда.
*Причина:* `сравнимо()` сводила книжное `12345` и наше `0012345` к одному числу,
и строка считалась неизменившейся.
*Починка:* сравнение **парное** и порядок доводов важен: где наше значение
помечено апострофом, сравниваем текст с текстом; для остальных — числовое
приведение, иначе SKU, который мы шлём строкой, а книга отдаёт числом, вечно
считался бы изменённым.
*Чем закрыто:* `проба/лист.test.js` — «артикул с ведущим нулём чинится, хотя как
число он равен книжному».

**№9. Починка артикулов отменяла сама себя.**
*Признак:* артикул чинится и снова портится через прогон — «качели».
*Причина:* при большом числе правок код переписывал блок целиком, включая
прочитанное из книги. Апостроф-пометка из книги не возвращается, и правильный
текстовый артикул при обратной записи снова разбирался как дата.
*Починка:* в книгу уходят **только наши** строки; ветка полной перезаписи удалена,
записи идут пачками по 200 диапазонов.
*Чем закрыто:* `проба/лист.test.js` — «в книгу не уходит ничего, прочитанного ИЗ
книги».

**№12. Шапка затирала чужие заголовки.**
*Признак:* своя формулировка или формула в заголовке заменилась значением.
*Починка:* заголовки дозаполняются **ровно в пустые клетки** первой строки и
отдельными диапазонами.
*Чем закрыто:* `проба/лист.test.js` — «занятые клетки шапки не трогаем».

### В. Запись в книгу (№10, №11)

**№10. Пустой ответ стирал лист остатков.**
*Признак:* лист остатков внезапно пуст, прогон отмечен успешным.
*Причина:* снимок перезаписывается целиком, а очистка хвоста шла до записи.
*Починка:* ноль строк в снимке — ошибка, лист не трогается. И порядок: сначала
пишем, потом убираем хвост, чтобы обрыв между шагами оставил данные.

**№11. Дозапись ложилась поверх невидимых строк.**
*Признак:* строки за 50 000-й затираются.
*Причина:* сервис читает лист до `ПРЕДЕЛ` строк и строит по ним указатель ключей;
то, что за пределом, не находится и дописывается заново.
*Починка:* лист, дочитанный до предела, останавливает дозапись с просьбой
перенести старое в архив. Плюс предупреждение «пора в архив» на 90 % предела.

### Г. Расписание и настройки (№13–№18)

**№13. Проходы шли внахлёст.**
*Признак:* в журнале одна и та же задача в двух-трёх экземплярах; в листе
задвоения.
*Причина:* задача может идти дольше минуты, а таймер тикает всё равно:
«Последний запуск» ещё не записан, `пора()` снова говорит «да».
*Починка:* флаг `идёт` в `тик()`; пропущенный тик пишется в журнал.

**№14. Упавший прогон сдвигал окно вперёд.**
*Признак:* после единичной ошибки заказы за этот период не выгружаются уже
никогда.
*Причина:* «Последний запуск» отмечает попытку, а не успех, и период считался от
него.
*Починка:* метка успеха дописывается в текст «Результата» хвостом
`| успех: ДД.ММ.ГГГГ ЧЧ:ММ:СС` и вычитывается оттуда (`успехИз`). Период считается
от последнего **успеха**.
*Чем закрыто:* `проба/настройки.test.js` — «метка успеха переживает ошибку».

**№15. Дата в колонке D игнорировалась.**
*Признак:* возвраты грузятся целиком, хотя «С даты» заполнена.
*Причина:* в блоке возвратов обе колонки, D и E, озаглавлены «С даты», а код
читал только E.
*Починка:* берётся та колонка, которая разбирается в настоящую дату. Не первая
непустая: пробел, ноль или оставшаяся подпись в E иначе отбросили бы дату из D.
*Чем закрыто:* `проба/настройки.test.js` — четыре случая на колонки D и E.

**№16. Глубина принималась за дату.**
*Признак:* глубина `31` читается как 31 января 1900 года.
*Починка:* отличие по году — настоящая дата имеет год ≥ 2015.

**№17, №18. Задача ниже блока была невидима.**
*Признак:* вписали задачу в книгу, она не запускается и ничего не говорит.
*Причина:* блок читался строго до `задачиДо`; строка ниже не попадала в чтение
вовсе. Именно на этом и погорели, когда задачу «WB заказы проверка» завели в
строке 61 при `задачиДо: 60`.
*Починка:* `задачиЗапас` — пять строк ниже блока дочитываются ради
предупреждения. Имена задач замкнуты, поэтому ложной тревоги быть не может.
*Чем закрыто:* `проба/настройки.test.js` — «строка 61 входит в блок задач»
(проверка **абсолютная**: относительная не замечала бы сужения блока обратно) и
«задача ниже блока не запускается, но и не молчит».

### Д. Период (№19, №20)

**№19. Простой дольше глубины терял заказы.**
*Признак:* сервис стоял три недели при глубине семь дней — заказы за эти две
недели не появились.
*Починка:* если водяной знак старше окна, окно растягивается назад до него
(минус час запаса).

**№20. Дыра в истории выглядела как штатное сужение.**
*Признак:* в «Результате» тот же текст, что в обычный день, а изменения статусов
за простой потеряны безвозвратно.
*Причина:* лента заказов сужает окно под предел метода в 31 сутки и не различала,
срезает она излишек или растянутое простоем окно.
*Починка:* `период()` возвращает `растянутоЗнаком`; коннектор пишет `ПРОПУСК
ИСТОРИИ` с границами пропуска.
*Чем закрыто:* `проба/лента-заказов-вб.test.js` — «дыра в истории после простоя
называется отдельно от штатной обрезки».

### Е. Пагинация (№21–№26, №31–№34, №36)

Самый дорогой класс. Все дефекты здесь выглядят как успешная работа.

**№21. `limit: 1000` у отправлений Ozon.**
*Признак:* `400 invalid PostingFboListRequest.Limit: value must be inside range
(0, 100]`.
*Починка:* `ПАЧКА_ОТПРАВЛЕНИЙ = 100` — предел метода.

**№22. Ozon молча игнорировал `offset`.**
*Признак:* в листе ровно 100 строк. Запрос отвечает 200, выглядит рабочим.
*Причина:* у методов нового поколения поля `offset` нет, а неизвестные поля метод
молча выбрасывает — и на любой странице отдаёт одну и ту же первую сотню. Это
подтвердилось тем, что и v3 FBO, и v4 FBS застревали ровно на 100.
*Починка:* лестница — курсор, затем рез окна по дате последнего прочитанного,
затем делёж пополам. Нижние две ступени опираются только на фильтр по датам,
который заведомо работает. Подробный разбор — `docs/ozon-pagination.md`.
*Чем закрыто:* `проба/отправления-ozon.test.js` — восемь случаев, включая «в
запросе нет ни offset, ни dir».

**№23. Начало окна двигалось по дате страницы.**
*Признак:* отправления пропадают без единого слова.
*Причина:* это молчаливая ставка на то, что метод сортирует ровно по тому полю,
по которому считает период. Разойдись они — начало перескочит через хвост
сортировки.
*Починка:* двигается только конец окна. Рез конца такой ставки не делает: две
половины покрывают окно целиком при любом месте реза.
*Чем закрыто:* «сортировка не по полю фильтра — начало окна не двигаем».

**№24. Отправление на шве реза выпадало из обеих половин.**
*Починка:* правая половина начинается миллисекундой **раньше** реза; перекрытие
снимает указатель прочитанных.
*Чем закрыто:* «группы отправлений с одинаковой датой не теряются на шве».

**№25, №26. Курсор, который не двигает выборку.**
*Признак:* бесконечный список одних и тех же записей либо обход, упёршийся в
предел запросов с сообщением не о том.
*Починка:* новый курсор сверяется со старым; равный — ошибка. У возвратов Ozon
то же для `last_id`. Отдельно: полная страница, пришедшая одним мгновением,
ловится сразу — иначе обход сорок раз поделит окно пополам.

**№31. Короткая страница считалась концом выборки.**
*Признак:* выгружена половина заказов, прогон успешен.
*Причина:* у метода ленты нет ни `has_next`, ни общего числа, поэтому «страница
короче предела» — это **догадка**. Короткий ответ посреди обхода обрывал
выгрузку молча.
*Починка:* конец подтверждает **пустая** страница. Лишний запрос стоит минуты,
потеря половины заказов — дороже.
*Чем закрыто:* «ложная короткая страница посреди обхода не обрывает выборку».

**№32. Снимок брался один раз и не сверялся.**
*Признак:* заказы пропадают незаметно при многостраничной выборке.
*Причина:* данные ленты обновляются в реальном времени. Переснимет метод
данные — ответит 200 с **новым** `snapshotTime`, а мы продолжим листать по чужой
нумерации.
*Починка:* снимок задаёт первый ответ, остальные обязаны его повторить;
расхождение останавливает задачу. В первом запросе снимка быть не должно — метод
начал бы листать чужой, уже закрытый.
*Чем закрыто:* «метод переснял данные — падаем, а не листаем чужую нумерацию».

**№33. Отпечаток сравнивался только с соседней страницей.**
*Признак:* выборка ходит по кругу A→B→A и не ловится.
*Починка:* помним отпечатки **всех** страниц. Отпечаток берётся по
опознающим полям (`srid`, `nmId`, `chrtId`), а не по состоянию: статус и его
время меняются на ходу, и застрявшая страница перестала бы узнаваться.
*Чем закрыто:* «страницы по кругу A→B→A не крутятся бесконечно».

Отдельно: застрявший `offset` определяется по **отпечатку страницы**, а не по
«нет новых srid». Второе означало бы ещё и «srid повторяется», а это законно — и
честная выборка падала бы с жалобой на пагинацию.
*Чем закрыто:* «повторяющийся srid не выглядит застрявшим offset-ом».

**№34. Свёртка повторов шла молча.**
*Признак:* усохшая в разы выборка выглядит маленькой, но полной.
*Починка:* свёрнутое считается и попадает в «Результат».

**№36. Предел страниц был несоразмерен.**
*Признак:* час простоя расписания ради данных, которые в лист не влезут.
*Причина:* 50 страниц по 10 000 — полмиллиона заказов при ёмкости листа 50 000, и
каждая страница стоит минуты.
*Починка:* 10 страниц, и соотношение с ёмкостью листа закреплено пробой
(`ПРЕДЕЛЫ_ЛЕНТЫ` вынесены наружу именно для этого).

### Ж. Молчаливый успех (№27, №42, №43)

**№27. Фильтр по дате мог быть молча не применён.**
*Признак:* отчёт сообщает запрошенный период, а в листе записи за всё время.
*Причина:* метод возвратов Ozon принимает лишь одну дату за запрос, и молча
вернуть всё подряд ему ничего не стоит.
*Починка:* считаем, сколько записей пришло вне запрошенного отрезка, и пишем
`ФИЛЬТР НЕ ПРИМЕНЁН: N`. Отдельная тонкость: `new Date(null)` — это 1 января 1970
года, и без проверки типа каждая запись без даты поднимала бы ложную тревогу.
*Чем закрыто:* `проба/возвраты-ozon.test.js` — два случая.

**№42. Повторялись отказы, которые повтор не чинит.**
*Починка:* повторяются только 408, 425, 429 и всё ≥ 500. Остальные 4xx летят
наружу сразу.

**№43. Обрыв на приёме тела превращался в пустой успех.**
*Признак:* на снимках это означало «пришло 0 строк».
*Починка:* обрыв тела — временный отказ, идёт в повтор.

### З. Лимиты (№28, №29, №37, №40, №41)

**№28. Отчёт возвратов ВБ не отдаётся дольше чем за 31 день.**
*Починка:* окна по 30 суток, не больше 24 окон.

**№29. Лимит ВБ считается на аккаунт, а не на метод.**
*Признак:* второй запрос подряд гарантированно 429.
*Починка:* `неЧаще(ключ, мс)` держит паузу сам. Ключи разные у статистики,
аналитики, возвратов и ленты — это разные методы с разными лимитами.

**№37. Голое «HTTP 429».**
*Признак:* человек идёт искать поломку в коде.
*Причина:* у токена категории «Базовый» лимит ленты — один запрос в **три часа**,
и выборка длиннее одной страницы на нём невозможна в принципе.
*Починка:* ошибка называет категории токенов и их лимиты.

**№40, №41. Яндекс: интервал и формат даты.**
*Признак:* 400 `Invalid filters: interval between dates` на 33 днях; даты
разбираются неверно.
*Починка:* окна по 28 дней; `изЯМ()` разбирает `ДД-ММ-ГГГГ` по частям.

### И. Поля и схема (№30, №35, №38, №39)

**№30. Остатки ВБ FBO переехали на другой метод.**
*Починка:* `/api/analytics/v1/stocks-report/wb-warehouses`. В ответе нет ни
штрихкода, ни артикула продавца — только `nmId` и `chrtId`, поэтому первые две
колонки собираются из справочника карточек.

**№35. «Тип отмены» стоял при любом статусе.**
*Признак:* у проданного заказа в листе причина отмены.
*Причина:* спецификация определяет `cancelType` только при `status: "cancel"`.
*Починка:* поле заполняется только при отмене. На проданном заказе причина
отмены — ложь, даже если метод её прислал.

**№38. Отказ справочника карточек затирал книгу.**
*Признак:* артикулы и штрихкоды в листе внезапно стали прочерками — и обратно не
вернулись.
*Причина:* это была «мягкая деградация»: при отказе справочника в строку
ставились прочерки. Но `сохранить()` пишет строку **целиком**, то есть затирала
уже выгруженные значения. Вернуть их следующим прогоном нельзя: заказ со статусом
старше тридцати суток лента больше не отдаёт.
*Починка:* справочник обязателен, его отказ останавливает выгрузку. Текст ошибки
называет справочник прямо, чтобы не искать поломку в самой ленте.
*Чем закрыто:* «недоступный справочник останавливает выгрузку, а не затирает
книгу».

Это **урок про деградацию в целом**: прежде чем переживать отказ части данных,
проверьте, как устроена запись. Там, где пишется строка целиком, «нет данных»
неотличимо от «затри то, что было».

**№39.** См. №20.

### К. Ламода и М.Видео (№45–№51)

Эти нашлись уже в коде другой системы (PR #12–#14) и в первых прогонах
FBO М.Видео. Общий урок у них один: **ответ, который нельзя отличить от
другого, — это ещё не ответ.**

**№45. 404 на карточке одного заказа Ламоды ронял всю выгрузку.**
*Признак:* «ОШИБКА: Lamoda /v2/orders/RU…: HTTP 404» — и ни одного заказа ни в
FBO, ни в FBS, так до тех пор, пока этот заказ остаётся в окне.
*Причина:* список заказов отдаёт только шапки, позиции берутся из карточки
каждого заказа отдельным запросом, и любая ошибка этого запроса летела наружу.
Чаще всего 404 даёт заказ, созданный только что: в списке он уже есть,
карточки ещё нет.
*Починка:* на 404 пробуется второй номер из шапки (`orderId` и `id`), если он
другой; не нашлось — заказ пропускается и **называется** в «Результате»; окно
«Глубина дней» перечитывается каждый прогон, и следующий его заберёт. Если не
нашлась ни одна карточка — это системная ошибка, а не свежие заказы: задача
падает и перечисляет поля шапки, чтобы было видно, какой номер ждёт метод.
*Чем закрыто:* четыре пробы в `проба/ламода-мвидео.test.js`.

**№46. Запасной адрес М.Видео был невидим.**
*Признак:* задачи М.Видео «успешны», но данные странные; 404 на методе, который
должен быть.
*Причина:* код ходит на `omni-net.sellers.mvideo.ru`, а если первый запрос за
жизнь процесса упал — навсегда переключается на `api.omniom.ru`, другую
систему. Ни один результат и ни одна ошибка не говорили, с какого адреса пришёл
ответ, поэтому «404 у М.Видео» и «404 у omniom» были неразличимы.
*Починка:* ошибка запроса называет адрес в квадратных скобках; результат каждой
задачи М.Видео, если адрес запасной, кончается словами «ЧЕРЕЗ ЗАПАСНОЙ АДРЕС».
*Чем закрыто:* «запасной адрес виден в «Результате»» и «ошибка запроса называет
адрес» — вторая на поддельном сервере.
Сам выбор адреса на всю жизнь процесса не исправлен — см. раздел 13.

**№47. Строки FBO-остатков М.Видео, приди они, отбрасывались бы.**
*Признак:* «FBO остатки Мвидео» писали «в API М.Видео нет схемы FBO», хотя по
коду этого видно не было.
*Причина:* по стандарту omninet `stock/info` отдаёт строки и со своего склада
(`location_id`), и со склада площадки (`market_location_id` без `location_id`).
Код верно отличал вторые как «не FBS» — и отбрасывал, никуда не передавая.

**Важная оговорка, и это урок.** Первая версия этой записи называлась
«FBO-остатки приходили и выбрасывались» — и это было неверно. Вывод сделан из
того, что в коде стоял фильтр на такие строки, а не из данных. Первый же прогон
с разбивкой ответа (05.11.2026) показал: 40 строк, все со своего склада, со
склада площадки — ни одной. Выбрасывать было нечего. **Фильтр в коде — не
доказательство того, что данные, которые он отбрасывает, существуют.**
*Починка:* `разделитьОстатки()` делит один ответ на две схемы. Когда FBO-строк
нет, ошибка даёт разбивку всего ответа — нулевых, на складе площадки, на своём,
без склада — и имена полей строки: по ним видно, не зовётся ли количество или
склад иначе, чем ждёт код. Лист при этом не перезаписывается.
*Чем закрыто:* пробы на разделение, на сбор строк и на текст разбивки.

**№48. «Схема не подключена» выглядела как «ошибка в запросе».**
*Признак:* «400; до этого вид тела 1, 2 — тоже 400».
*Причина:* первая страница М.Видео перебирает три вида тела на любой 400. Но
стандарт omninet на неподключённую кабинету схему отвечает
`400 OPERATION_NOT_SUPPORTED`, и никакой вид тела этого не вылечит.
*Починка:* на `OPERATION_NOT_SUPPORTED` перебор прекращается сразу, а задача
говорит «FBO для этого кабинета не подключён».
*Чем закрыто:* «OPERATION_NOT_SUPPORTED не перебирает виды тела» и парная к ней
«на обычном 400 перебор по-прежнему работает».

**№49. Ключ М.Видео уходил одним способом, не тем, что велит стандарт.**
*Признак:* пока никакого — и в этом опасность. Шлюз принимает ключ в `api-key`.
Но стандарт omninet (omni-net.dev/spec/fbo/common/auth) требует для всех схем
`Authorization: Bearer` и прямо пишет, что `Client-Id` + `Api-Key` в его же
OpenAPI FBS/FBO — расхождение, которое поправят «в ближайшей выкатке». Если
шлюз М.Видео пойдёт за стандартом, все задачи М.Видео упадут с 401. И второе: вывод «у М.Видео нет FBO» (05.11.2026)
сделан по 404 на `api-key` — Bearer, единственный способ по стандарту, на FBO
никто не пробовал.
*Причина:* до 02.11.2026 ключ уходил в обоих заголовках сразу, и шлюз отвечал
«HTTP 400» на список товаров. Bearer убрали в одной правке с перебором видов
тела (№48 стоит на том же месте), так что что именно лечило, не установлено, —
но вывод «лишний заголовок ломал запрос» попал в комментарий как факт.
*Починка:* `сКлючом()`. Схем две, и `api-key` — эталон: с ним код работал до
правки, на нём построены проверки «не подключено» (404/403).
- Первым идёт схема, на которой метод последний раз **вернул данные**; метод,
  который ещё не отвечал, — с `api-key`. Общей для всех методов схемы нет.
- Вторая схема пробуется, если первая — `api-key` и ответила 401, 404 или
  `400 OPERATION_NOT_SUPPORTED` (вывод «не подключено» по одной схеме ключа —
  вывод только про неё), или если первая — запомненный Bearer и не прошла
  ничем (возврат к эталону). Проба Bearer после 404 и
  `OPERATION_NOT_SUPPORTED` — одна попытка, без повторов и пауз: её неудача
  ничего не решает. Bearer после 401 и возврат к `api-key` — с обычными
  повторами: их ответ решает исход.
- Прошла хоть одна — её данные, схема запоминается для метода.
- Не прошла ни одна — решает ответ `api-key`. Ответ Bearer решает, только если
  `api-key` отвергнут (401), а Bearer — нет: ключ принимается одним Bearer, и
  его ответ — настоящий ответ метода (раньше такой запрос падал с 401, а пока
  адрес не подтверждён — уходил на запасной адрес).
  Другой ответ дописан справкой, из которой убраны слова, по которым код
  принимает решения («HTTP 400», OPERATION_NOT_SUPPORTED). А сами решения —
  смена адреса, перебор видов тела, «не подключено», терпимость к DBS —
  читают только текст решающего ответа (`решающийТекст()`): сетевых слов
  справка не обезвреживает. У ошибки есть `статусы`: [api-key, Bearer].

Отсюда инвариант: **если Bearer не прошёл, а `api-key` не получил 401, всё —
какая ошибка, терпится ли она, адрес, перебор видов тела — так же, как до
правки.** Исключений два, и оба — про ответ метода, а не про схему ключа: 404
заказов FBO не меняет адрес (№50), а `OPERATION_NOT_SUPPORTED` на DBS терпится
так же, как 404/403, — по стандарту так отвечает неподключённая схема, и иначе
переход шлюза на Bearer ронял бы обе задачи FBS у кабинета без DBS. Пометка
«ключ в Authorization: Bearer» в «Результате» — только по успехам. Ошибка «Заказы Мвидео FBO»: 404 на обеих схемах — «нет метода ни с
одной схемой ключа»; разные ответы — «не отдал заказы ни с одной схемой ключа:
api-key — 404, Authorization: Bearer — 401»; тело ответа шлюза остаётся в
тексте. При уходе на запасной адрес ответ шлюза М.Видео пишется до 600 знаков
(раньше — 120). На `api.omniom.ru` второй попытки нет: туда ключ и так уходит
обоими заголовками.

**Шесть первых версий этой починки были неверными и в прод не попали.** Каждую
перед мержем разбирали три рецензента, каждую находку — два скептика, и все
подтверждённые находки воспроизведены.
- Первая давала решать ответу Bearer, если тот был не 401/404, и запоминала
  Bearer даже после его неудачи. Где DBS не подключён (`404` на `api-key`, его
  терпят), ответ Bearer 400/429/5xx или сбой связи ронял «Заказы Мвидео FBS» и
  «FBS остатки Мвидео»; один сбой связи закреплял Bearer до перезапуска.
- Вторая держала общую схему: один «api-key 401, Bearer прошёл» переводил на
  Bearer методы, ни разу на нём не ответившие, — и их Bearer 400 снова ронял
  задачи FBS до перезапуска. Ещё в ней запомненный Bearer не возвращался к
  `api-key`, справка о второй схеме включала «не подключено», а проба на 5xx
  повторялась пять раз с паузами.
- Третья давала возврату с запомненного Bearer к `api-key` одну попытку:
  разовый 500 ронял прогон, который прежний код пережил бы повтором. И в ней
  была неверная первая версия №50 (см. ниже).
- Четвёртая давала одну попытку и Bearer после 401, хотя его ответ решает: в
  мире Bearer разовый сбой связи первым запросом после перезапуска уводил
  процесс на запасной адрес. Ещё она не пробовала Bearer на
  `OPERATION_NOT_SUPPORTED` и терпела это слово у DBS при любом статусе, даже
  в теле пятисотки. Находки четвёртого разбора скептики сочли не дефектами
  относительно прода, но правки дешёвые и закрывают дыры, так что сделаны.
- Пятая, научившись пробовать Bearer на `OPERATION_NOT_SUPPORTED`, открыла
  старую щель: выбор адреса читал ошибку целиком, со справкой. «api-key 400
  OPERATION_NOT_SUPPORTED, Bearer — fetch failed» первым запросом после
  перезапуска (заказы FBO у кабинета без FBO, каталог, склады FBS) уводил весь
  процесс на `api.omniom.ru`. Справка обезвреживала слова решений про тело и
  подключение, а сетевые — нет. Теперь решения читают только решающий ответ.
- Шестая не дала решающего текста ошибке после ухода на запасной адрес. Там
  решения читали и «до этого» — ответ шлюза М.Видео, который правка стала
  писать до 600 знаков вместо 120, — и `OPERATION_NOT_SUPPORTED` или «HTTP 400»
  из его тела решали на `api.omniom.ru`: останавливали перебор видов тела или
  запускали лишний. Теперь решает ответ последнего адреса.
Урок: **проба, которая не прошла, не должна менять ни исход, ни следующий
запрос — ни для своего метода, ни для чужих.** И второй: список «опасных слов»
расходится с тем, что код на деле читает; надёжнее, чтобы решения читали
только то, что решает.

*Чем закрыто:* тридцать пять проб в `проба/ламода-мвидео.test.js`,
четырнадцать из них гоняют задачи целиком на поддельном шлюзе и поддельной
книге (`проба/поддельная-книга.js`). Пробы по находкам разборов падают на той
версии, где находку нашли: DBS не подключён и Bearer отвечает 400/403 — FBS
пишется, а подключённый позже DBS подхватывается; разовый 401 не переводит DBS
на Bearer; FBO только на Bearer не ломает FBS; проба на 503 — одна попытка;
возврат к `api-key` и Bearer после 401 — с повторами; шлюз на Bearer и разовый
сбой связи первым запросом — адрес тот же; `OPERATION_NOT_SUPPORTED` первым
запросом и сбой пробы Bearer (сеть или пятисотка с «fetch failed» в теле) —
адрес тот же, для заказов FBO, складов FBS и каталога; решения читают
решающий ответ, а не справку, а после ухода на запасной адрес — его ответ, а
не «до этого»; DBS с `OPERATION_NOT_SUPPORTED` — «не подключён»
и на `api-key`, и на Bearer, а с данными на Bearer — данные пишутся; пятисотка
со словом `OPERATION_NOT_SUPPORTED` — сбой; справка не останавливает перебор
видов тела на запасном адресе. Остальные держат правила от отката: кто решает,
когда запомненный Bearer и `api-key` не прошли оба; пометка схемы — по каждому
методу своей задачи и только своей; DBS, ходивший через Bearer и потом
отключённый, — снова «недоступен»; DBS на 403 — «не подключён»; настоящий
отказ DBS (500, голый 400, 422) роняет задачу и не трогает лист. Ещё одна — на
настоящем HTTP-сервере: до шлюза доходит один заголовок ключа.
Мутаций семьдесят две (вместе с №50); ловятся шестьдесят девять. Три
уцелевших равносильны: статус ошибки читается по первому «: HTTP nnn», а
решающий ответ всегда идёт первым, справка же — без «HTTP»; терпимость к
неподключённому DBS и к складам площадки читала бы и «до этого», но их методы
никогда не идут первым запросом процесса, так что ошибки после ухода на
запасной адрес до них не доходят, а справка обезврежена. Две мутации прежних раундов показали лишние строки
(запоминать успех первой попытки; гасить пометку на omniom, где схема не
запоминается), и строки убраны.
Урок тот же, что у №47, с другой стороны: **вывод «X нет» верен ровно для того
способа, которым X искали.**

**№50. 404 на заказах FBO уводил весь процесс на запасной адрес.**
*Признак:* после перезапуска воркера «Заказы Мвидео FBS» и «FBS остатки Мвидео»
падают с «HTTP 401 … [api.omniom.ru]», хотя шлюз М.Видео для них исправен; в
«Результате» других задач — «ЧЕРЕЗ ЗАПАСНОЙ АДРЕС». Держится до перезапуска.
*Причина:* адрес шлюза выбирается первым удачным запросом процесса (№46), а 404
на непроверенном адресе считается «не тот хост». На шлюзе М.Видео
`/v1/order/fbo/list` отвечает 404 — метода нет. Если «Заказы Мвидео FBO»
оказывались первой задачей М.Видео после перезапуска, процесс уходил на
`api.omniom.ru`. Нашёл разбор кода PR #12–#14 (находка F2).
*Починка:* 404 на `/v1/order/fbo/list` не считается «не тот адрес»
(`МОЖЕТ_НЕ_БЫТЬ` в `другойАдрес()`): метода FBO на шлюзе может не быть, и его
404 — ответ метода. Решает статус решающего ответа, поэтому «api-key 401,
Bearer 404» — тоже 404 метода. Сетевая ошибка и 401 на обеих схемах адрес
меняют, как раньше.
Первая версия починки (в прод не попала) подтверждала адрес вызовом
`/v1/merchant/location/list` перед FBO. Третья проверка показала, что так
исход FBO зависел от метода FBS-складов: у кабинета без FBS его отказ ронял
каждый прогон «Заказы Мвидео FBO», а его 404 или 401 уводил на запасной адрес
весь процесс — то самое, от чего чинили. Урок: **чинить надо то решение, которое
ошиблось (404 метода принят за 404 адреса), а не подпирать его ещё одним
запросом, у которого свои отказы.**
*Чем закрыто:* пять проб: «заказы FBO первыми после перезапуска не уводят
процесс на запасной адрес»; «… не зависят от методов FBS» (отказ FBS-складов
400 `OPERATION_NOT_SUPPORTED`, 404, 500 — FBO пишется); «404 на заказах FBO …
не меняет адрес, что бы ни ответил Bearer» (404, 401, 403, 500, сбой связи, и
«api-key 401, Bearer 404»); «401 на заказах FBO … адрес меняет, как раньше»;
«сбой связи на заказах FBO … адрес меняет, как раньше». Шесть мутаций
(исключения нет; путь не передан; исключение на любую ошибку; и на 401; только
при 404 на обеих схемах; на всё, кроме 401).

**№51. Остатки FBO М.Видео спрашивались только без фильтра по складам площадки.**
*Признак:* «FBO остатки Мвидео»: «ненулевых остатков на складах площадки нет —
пришло 40: нулевых 40, на складе площадки 0, на своём складе 40; поля строки:
product_id, offer_id, location_id, count, available_count» (прод, 05.11.2026).
*Причина:* у `/v1/product/stock/info` по стандарту два контракта на одном
пути. FBS фильтрует по `location_id` и отвечает строками с `location_id`; FBO —
по `market_location_ids` и отвечает строками с `market_location_id`. Запрос без
фильтра годится обоим (поля фильтра необязательны), но шлюз М.Видео ответил на
него строками контракта FBS — по полям строки это видно. Меняет ли это фильтр
по складам площадки, никто не спрашивал: вывод «FBO-остатков нет» был сделан по
одному запросу — урок №47 и №49 с третьей стороны.
*Починка:* если без фильтра строк со склада площадки нет, `мвОстаткиFboСтроки()`
берёт склады из `/v1/market/location/list` и спрашивает остатки ещё раз, с
`filter.market_location_ids`. Схема ключа и вид тела этого запроса помнятся
отдельно, под именем `ОСТАТКИ_FBO`, а не под путём: разбор нашёл, что иначе
удача Bearer в форме FBO отправляла на Bearer и остатки FBS — до перезапуска.
Ошибка без FBO-строк начинает с вывода по форме FBO — ячейка «Результата»
короткая: справочника складов нет (404), к нему нет доступа (403), справочник
ответил `OPERATION_NOT_SUPPORTED` (FBO не подключён), справочник пуст, «по
складам площадки (N: …) пришло …» (фильтр не понят — те же строки FBS) или
запрос не прошёл — с причиной: статусом, а без него самим отказом («fetch
failed», «ответ без списка «stocks»», «ответ не JSON»); дальше разбивка ответа
без фильтра, ответ шлюза целиком — последним. Отказ справочника терпится, как у
DBS, только на 404/403 и решающем 400 `OPERATION_NOT_SUPPORTED` (`методНеПодключён()`):
пятисотка со словом в теле — сбой. Нашлись строки — лист пишется, в «Результате» «по фильтру складов
площадки». Без фильтра — по-прежнему первым: он подтверждает адрес, а 404
справочника первым запросом процесса увёл бы на запасной.
*Чем закрыто:* шесть проб: в форме FBO спрашивается по складам справочника и
пишет строки; ошибка — вывод первым, во всех исходах (справочника нет, 403,
не подключено, фильтр не понят, складов больше пяти, отказ запроса и пятисотка
со словом `OPERATION_NOT_SUPPORTED`, ответ 200 без списка, не JSON и с
застрявшим курсором, пустой справочник, 500 справочника — сбой, и со словом
`OPERATION_NOT_SUPPORTED` в теле тоже);
вид тела формы FBO помнится отдельно; обход передаёт имя памяти на каждой
странице; Bearer в форме FBO не переводит на Bearer остатки FBS, а форма FBO
свою схему помнит; задача целиком — без фильтра 40 нулей FBS, как в проде 05.11,
и справочник с 404 маршрутизатора. Последнее — допущение: в проде 05.11
справочник не спрашивали. Мутаций тридцать три, ловятся все.
Урок: **другой контракт на том же пути — другой метод для всего, что код о
методе помнит.**

## 12. Метод: как здесь принято работать

### Правило про пробы

> Починка принимается только вместе с пробой, про которую **доказано**, что на
> прежнем коде она падает.

Проба, которая проходит и на старом коде, ничего не проверяет. Проверять это надо
руками:

```bash
git stash          # убрать починку, оставить пробу
npm test           # проба ОБЯЗАНА упасть
git stash pop      # вернуть починку
npm test           # проба обязана пройти
```

Это не формальность. В этой работе пустые пробы попадались **трижды**:

* проба на обратную запись брала 300 строк, а порог срабатывал с 200 диапазонов —
  до него просто не доходило. Переписана на 500 строк;
* проба на блок задач брала `задачиДо` из кода, поэтому сужение блока обратно до
  60 не замечала. Переписана на абсолютный номер строки;
* проба на подсунутую чужую шапку давала лист в три колонки, а проверка
  содержимого включается только при совпадении ширины — старая логика просто не
  могла ошибиться. Переписана на лист той же ширины с данными.

### Мутационная проверка

Надёжнее `git stash`: ломать каждую защиту по очереди и смотреть, какая проба
ловит. В этой работе так проверены все починки ленты заказов (14 мутаций),
диагностика (6 мутаций) и проверка документации (9 мутаций). Шаблон — любой из
скриптов в истории: подменить кусок кода, прогнать пробы, вернуть кусок,
посмотреть на код возврата.

Мутация, которую никто не поймал, означает одно из двух: пробы нет или она
пустая. Оба случая требуют работы.

### Три приёма, которые здесь многократно оправдались

**Поддельный сервер вместо живого API.** Повадки методов — пределы периода,
пагинацию, лимиты, формат ошибок — на живом API не проверить: он либо работает,
либо лимитирован. Поддельный сервер на localhost ведёт себя как настоящий
(отвергает период длиннее предела, требует `snapshotTime` там, где положено) и
проверяется в миллисекундах. Адреса для этого вынесены в переменные окружения.

**Шов для подмены книги.** `подставитьКлиент()` в `sheets.js` позволяет
проверить запись, и именно в записи сидели две самые дорогие ошибки (№7, №9). На
живом API их было не найти.

**Поддельная книга должна врать как настоящая.** Фальшивые Таблицы в
`проба/лист.test.js` снимают апостроф, разбирают даты и числа по-своему и **не
возвращают апостроф при чтении** — на этом и горел код. Поддельная книга, которая
отдаёт то, что в неё положили, не проверяет ничего.

### Что проверяет сама себя

| Команда | Что сверяет |
|---|---|
| `npm test` | поведение, 72 случая |
| `npm run диагностика` | наличие всех известных починок |
| `npm run проверить-ссылки` | документация против кода: файлы, адреса методов, имена констант и переменных, диапазоны настроек, имена листов |
| `npm run свод` | пересобирает `docs/ves-kod.md` |

**Отдельный урок про документацию.** В `reestr-kodov.md` сначала были ссылки
вида `файл.js:123`, и проверка сверяла номера строк. Это оказалось **хуже, чем
ничего**: номер устаревает от любой вставки, а проверка «строка существует и не
пуста» съехавшую ссылку пропускает — документ продолжает выглядеть точным,
указывая не туда. Попались дважды, во второй раз соврали сразу тридцать две
ссылки. Теперь номеров строк в документации нет вовсе, а сверяется содержимое.

И ещё: эта самая проверка один раз нашла имя константы **в собственном
комментарии** и промолчала. Сверка идёт только с `src/` — пробы держат поддельные
серверы с теми же адресами, служебные скрипты — пояснения с именами констант, а
свод и вовсе содержит весь код целиком.

### Как разбирать свой же свежий код

Состязательный разбор по нескольким независимым направлениям с проверкой каждой
находки нашёл в этом коде то, что автор считал готовым: **два блокирующих дефекта
и десять помельче**, из них два — в общем коде, затрагивающем уже работающие
листы. Ни один не был виден при обычном перечитывании диффа.

Что из этого стоит перенять:

* направления должны быть **независимыми и разными**: спецификация, пагинация,
  период и часовые пояса, запись в книгу, влияние на уже работающее. Пять
  одинаковых проверяющих найдут одно и то же;
* каждую находку надо **пытаться опровергнуть**, а не принимать. Из шестнадцати
  находок две были отклонены по существу, и обе справедливо — в одном случае
  предложенная «починка» записала бы в книгу ложь;
* **своё обоснование тоже проверяется.** Один раз я оставил находку с
  объяснением «лента — самая долгая задача, часа не идёт». Проверяющий это
  опроверг: лента ограничена десятью страницами, а отправления Ozon ходят до 500
  запросов при том же часовом запасе.

## 13. Известное и не сделанное

Эти вещи разобраны, поняты и оставлены — сознательно. Если вы будете их чинить,
начните с того, почему их не починили.

**Запас в час не покрывает длительность прогона.** Метка успеха пишется в
**конце** прогона, а окно того прогона кончалось в **начале**. Перехлёст равен
часу минус длительность прогона. Если прогон шёл дольше часа и затем случился
простой дольше глубины, между окнами остаётся непокрытый зазор — молча, без
пометки. Дефект давний, общий для всех задач с `период()`, и опаснее всего не для
ленты (10 страниц), а для отправлений Ozon (`ЗАПРОСОВ_МАКСИМУМ` 500) и для обхода
карточек (до 200 страниц без ограничителя частоты). Последствие мягче, чем
кажется: заказ, уже записанный прошлым прогоном, не исчезает — у него **замирает
статус**; исчезают только те, чья жизнь целиком попала в зазор.
*Безопасная починка:* считать запас от начала прогона — `min(знак, старт) −
ЗАПАС`. Очевидный вариант «писать в метку конец окна» **сломает `пора()`**: колонка
F служит и меткой успеха, и временем последнего запуска.

**`описаниеПериода` вызывает `период()` второй раз, после прогона.** Поэтому у
задач «Заказы *» в «Результате» печатается конец периода позже фактически
выгруженного. Мелочь, но это неправда в отчёте.

**Задвоение строк у Яндекса и Ламоды.** Артикул входит в ключ строки. Если в
одном заказе два одинаковых артикула разных размеров — строки схлопнутся. Убрать
артикул из ключа нельзя: тогда схлопнутся все товары многотоварного заказа. Нужен
размер или ID позиции в ключе, а их метод не всегда отдаёт.

**История Яндекса глубже месяца недоступна** — ограничение метода. То же у ленты
заказов ВБ: глубже 31 суток метод не отдаёт.

**Адрес шлюза М.Видео выбирается раз на всю жизнь воркера.** Если первый
запрос к `omni-net.sellers.mvideo.ru` за жизнь процесса упал — разовый сбой, 404
или 401 на обеих схемах ключа (№49), — все дальнейшие уйдут на `api.omniom.ru`,
пока процесс не перезапустят. Теперь это хотя бы видно (№46), но не исправлено.
404 заказов FBO адрес не меняет — это ответ метода, а не адреса (№50).
Схема ключа тоже запоминается на всю жизнь процесса, но только по успехам и
только для своего метода (№49): неудача её не меняет, а метод, переставший
отвечать на запомненной, сам пробует другую.

**Авторизация М.Видео расходится со стандартом — пока.** Стандарт omninet
требует `Authorization: Bearer` для всех схем; шлюз М.Видео принимает `api-key`.
Код идёт с `api-key`, а на 401, 404 и `OPERATION_NOT_SUPPORTED` сам пробует
Bearer (№49). Когда М.Видео
перейдёт на Bearer, в «Результате» появится «ключ в Authorization: Bearer», и
задачи продолжат работать сами: каждый метод после первого «api-key 401, Bearer
прошёл» идёт сразу с Bearer, а неподключённый DBS терпится, как бы шлюз на
него ни ответил: 404, 403 или, по стандарту, `400 OPERATION_NOT_SUPPORTED`.
Ответ Bearer после 401 получает обычные повторы, так что разовый сбой связи на
нём адрес не меняет. Схема запоминается по успеху HTTP (2xx), а не по
содержимому: если шлюз на Bearer ответит 2xx без списка — пустым телом или
ошибкой в JSON — вместо 401/404/400, метод закрепится на Bearer до перезапуска
и будет падать с «ответ без списка» (видно в «Результате»), а пустой список
запишется как «0 строк» с пометкой «ключ в Authorization: Bearer». Шлюз
М.Видео так не отвечает — отказы у него со своими статусами; разборы дважды
сочли это не дефектом, а если увидите — перезапустите воркер.
Менять порядок схем в коде тогда можно, но не
обязательно — это сэкономит один запрос на метод после перезапуска. Пару
`Client-Id` + `Api-Key` стандарт запрещает, и код её не шлёт.

**`ПРЕДЕЛ` 50 000 — потолок листа.** При подходе задача падает намеренно;
архивирование не автоматизировано.



**`srid` в «Заказы ВБ FBO» пишется без `строгоТекстом`.** Пока `srid` приходит в
виде `7513…943.1.0`, Таблицы его не тронут — там две точки, это не число. Если
ВБ отдаст чистый `odid` числом, ключ начнёт плыть. Починка №7 закрыла худшее
(схлопывание ключей), но сама колонка не защищена принудительно. Правка ключа на
живом листе требует перезаписи истории, поэтому оставлена как решение владельца.
